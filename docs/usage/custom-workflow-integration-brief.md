# Custom workflow integration brief

Use this short brief to agree what the workflow needs and what the approved environment actually provides. Resolve gaps before activation or external action.

| Question | Record the answer |
| --- | --- |
| What outcome is needed? | User, decision, requested artifact and completion checks |
| What evidence is needed? | Required fields, sources, dates, missingness and conflicts |
| What is available? | Existing host/account, file access, approved evidence environment and optional local CLI |
| How will the pack load? | Exact file paths or host-supported install method; proof of actual reads or activation |
| Which tools are needed? | Only the compact set required for this task; owner and authority for each external action |
| What remains unavailable? | Missing access, unqualified client, unsupported calculation or unresolved policy |
| Who reviews and approves? | Draft review, domain acceptance, recruitment/consent/outreach and operational handoff |
| How will it change or end? | Revision identity, retest triggers, removal and retirement owner |

The generated custom pack contains instructions and a case template. `admin export` supports the six catalog workflows; it is not a generic custom-pack installer. A custom pack does not register a service or tool, authorize outreach, or provide a general orchestration runtime. Use explicit file loading when that fits the existing approved host, and record what actually loaded.

Select a small set of tools to meet a stated need. Add integrations only when the task requires them and the owner has approved their access and actions. For packaged integrations and their tested limits, consult [Installation](../../INSTALL.md) and the [developer reference](development-checks.md#integration-developer-reference).
